# Queensland Interactive Server

This Express server serves the website and proxies requests to Roblox and TikTok. For self-hosting instructions, see [docs/SELF_HOSTING.md](../docs/SELF_HOSTING.md).

## Quick start

```bash
cd server
npm install
npm start
```

The server listens on all network interfaces at port `3000` by default. Set `HOST` or `PORT` to change this. Check connectivity with `http://SERVER_ADDRESS:3000/api/health`. For public access, keep Node on port `3000` and use a router port forward plus an HTTPS reverse proxy.

Feedback is submitted through `/feedback.html` and delivered using `DISCORD_WEBHOOK_URL`.

## Environment variables

Copy `.env.example` to `.env`, then set the values required by your deployment. The provided start scripts load this file. Never commit `.env`.

The server exposes Roblox, TikTok, feedback, moderation, Discord OAuth, notification, and live status endpoints under `/api` and `/auth`. QLiTE Roblox player search, profile, and avatar lookups use the server-side `/api/roblox/users/search`, `/api/roblox/users/:userId`, and `/api/roblox/users/:userId/avatar` routes, so deploy the server when changing those dashboard features. Search results are cached briefly, and Roblox search rate limits are returned to the dashboard with a retry delay.

QLiTE sign-in requires Discord OAuth, `TRELLO_API_KEY`, `TRELLO_API_TOKEN`, and `QLITE_LOGINS`. Set `QLITE_LOGINS` to Discord **user IDs** permitted to sign in, for example `123456789012345678,987654321098765432`; usernames are not accepted. IDs may be comma-, whitespace-, or newline-separated, and Discord mention forms such as `<@123456789012345678>` are also accepted. An empty or unset list disables QLiTE access. This allowlist grants eligibility only; it does not create an account. Each person must verify their own allowlisted Discord account and create a QLiTE password once, then use that Discord username/ID and password to sign in. After changing access-list variables, restart the API service so it loads the new list. If a user is rejected, the sign-in page shows their Discord ID to compare against the access list. Admins who use QLiTE must also be included in this list and in `ADMIN_USER_IDS`. `QLITE_ALLOWED_ORIGINS` is a comma-separated allowlist for QLiTE browser requests; it defaults to the configured `WEBSITE_ORIGIN` and `WEBSITE_STATUS_URL` origins, with the production `www` hostname also allowed. Add any alternate deployment hostname there. Set `TRELLO_QLITE_ACCOUNTS_BOARD_ID` to the destination board; the server finds or creates a `QLiTE Accounts` list there. Optionally set `TRELLO_QLITE_ACCOUNTS_LIST_ID` to use a specific existing list instead. New users verify Discord, then set a password; returning users sign in with that password. Changing an existing password requires fresh Discord authorization; the authorization is valid for five minutes and is checked by the server. New and changed passwords must be 12–128 characters; previously saved passwords shorter than 12 characters remain valid. For brute-force protection, eight consecutive failed sign-ins temporarily lock that username/IP for one minute. The server stores only a salted scrypt password hash in `server/data/qlite-accounts.json`. OAuth state and login cookies are signed with `SESSION_SECRET` (or `DISCORD_CLIENT_SECRET` if unset), allowing those credentials to be verified across replicas; configure the same `SESSION_SECRET` on every replica. Password sign-in accepts the Discord username (with or without a leading `@`), the Discord user ID, or a uniquely matching Discord display name; passwords are case-sensitive. The server reloads the account file before password sign-in so newly saved account details are used. Trello cards contain Discord account metadata only, never passwords or password hashes. Archive an account card or move it out of the configured list to revoke password access. Admins listed in `ADMIN_USER_IDS` can view QLiTE account status and re-allow or revoke accounts in the Admin Panel; re-allowing restores the Trello card to the configured accounts list.

QLiTE player records are stored server-side in `server/data/qlite-records.json` and shared with signed-in users. Records can include Safety, DV, move-on directions, fines, warrants, Traffic, youth cautions, arrests, vehicle impounds, and person-linked field property receipts with descriptions, markings, and additional information. Impounds can include vehicle description, registration, and location. Property receipt serials are generated server-side in sequence beginning with `RBX1234`, and remain unique across active records and audit history. The dashboard opens on a Home page showing active warrants, latest record activity, latest property receipts, and latest arrest records. The centered top-bar search searches Roblox players (including numeric IDs), shared records and serial numbers; administrators can also search the full audit log. The player overview displays all record types together, newest first, and indicates whether arrest records exist; its record dropdown adds the selected type without filtering the record list. The Admin tab displays who added or revoked each record, with expanded details; this full audit trail remains admin-only. Only Discord IDs in `ADMIN_USER_IDS` can revoke records, enforced by the API as well as the dashboard. Roblox profile thumbnails are retrieved through the server proxy; pending thumbnail responses are not cached so the dashboard can retry while Roblox processes an image. On Railway, set `QLITE_LOGINS` and `ADMIN_USER_IDS` in the service variables, and attach a persistent volume at `/app/data` so account and record data survives redeploys (with the service root directory set to `server`). The JSON account and records files require a single server instance; multiple replicas need shared database storage to keep them consistent. Signed auth cookies let OAuth sessions work across replicas but do not synchronize account or player-record data.
